## D26 — decoded settings boundary

Decoded scalar settings live in a typed portable bag with separate raw migration adapters still pending. `settings::Context` supplies region and battery state; the app must obtain them through native boundaries. Notification results and hotkey replacements are data, with actual callbacks/registration performed by the app. Vote-ID allocation is an explicit lazy method with an injected GUID allocator; read-only snapshots must not create vote IDs. Initial migration must preserve unknown raw fields as well as unknown decoded keys. This separation does not change the legacy persistence or bridge contract.

## D27 — CLI snapshot plans

The portable CLI rule layer consumes nullable device/app snapshots, produces the original PascalCase plan DTOs and camelCase preview/apply/resolve responses, and can apply plans to a snapshot for deterministic tests. Native audio adapters must execute the same target selection and order rather than interpreting each plan row as one endpoint-local target. Source reference code runs against mutable view-model stand-ins, so these tests verify parsing/planning/serialization/selection, not native setters, dispatch or IPC. Captured numeric parsing currently uses en-US; other current-culture number-format contracts remain an explicit milestone 1 gate.

## D28 — milestone acceptance boundaries

Milestone sequencing follows the requested separation: milestone 1 verifies portable models, decoding/validation and golden serialization; native CLI provider/dispatcher/transport effects are accepted in milestone 3, and native app storage/startup/hotkey integration in milestones 4/9/10. PARITY states those boundaries explicitly. Every native acceptance item remains unchecked in its owning milestone.

## D29 — current-culture parsing boundary

`numbers::IntegerFormat` implements .NET 8 integer-style parsing from supplied positive/negative signs, including its hyphen compatibility list. CLI rule parsing accepts that format explicitly. Set-volume additionally takes a `CommandCulture` provider for the original CurrentCulture StartsWith comparison; ordinal/ASCII prefix tests cannot establish that contract. Core tests use captured .NET prefix results, and the installed dispatcher must supply and verify a native culture adapter in milestone 3 (MANUAL_TESTS 16). No OS collation backend has been accepted yet. Adaptation sources and the .NET MIT notice are in rust/THIRD_PARTY_NOTICES.md.

## D30 — legacy XmlSerializer decoding

`legacy_xml` decodes the registry/package/portable XML scalar, HotkeyData and WINDOWPLACEMENT values with a streaming cursor modelled on the original `XmlTextReader` (significant whitespace, no external resolution) rather than a DOM. Primitive roots follow `ReadElementString`, class members follow `ReadElementContentAsString`, and the class loop takes the first matching member. Parsing stops where the original stops, so trailing content is only validated if the original would read it. `quick-xml` supplies tokenization; character validity, root/DOCTYPE/declaration placement, xml:space and nil handling are enforced by the cursor. Windows Forms `Keys` names are a table generated from the .NET 8 runtime by the capture script. DTD internal subsets are tokenized but never applied (declared entities fail as in the reference; attribute defaults are ignored). Settings written by XmlSerializer never contain DTDs, so this is recorded rather than emulated. The decoder never opens files or the registry; store adapters remain milestone 1/4 work.

## D31 — settings bag read semantics

`legacy_store` reproduces each original bag's `Get<T>(key, default)` over raw values handed in by store adapters: registry values (REG_SZ only; other types read as the default), package LocalSettings (native bool/string, other types XML strings) and the portable `config/settings.json` bag. `NamespacedSettingsBag` is a `namespace.` key prefix. Registry and package XML failures surface as `Read::Throws` because the original lets the exception escape the getter; the portable bag catches everything and returns the default. Adapters must keep the raw value, log the condition and use the default instead of reproducing an unhandled getter exception. That is a deliberate deviation in failure presentation only.

The portable bag needs Newtonsoft.Json 13 semantics, implemented in `newtonsoft`: its lenient reader (comments, quotes, unquoted names, octal/hex, NaN/Infinity, undefined, empty array elements, trailing commas, NULs as whitespace, `new` constructors with the JTokenWriter `Date` validation), `DateParseHandling.DateTime` reparsing of ISO and `\/Date()\/` strings, and the `SerializeObject`→`DeserializeObject<T>` fallback (`ReadAsBoolean/Int32/Double/String`, `EnumUtils.ParseEnum`, `Convert.ChangeType` for uint fields, ordinal-then-ignore-case member matching). Local-time conversion of offset dates is a native boundary (`LocalZone`); tests use US Central rules checked against the offsets Windows reported during capture. `File.ReadAllText` BOM handling is `decode_text`. Unpaired UTF-16 surrogates become U+FFFD because Rust strings cannot hold them. Newtonsoft also writes U+FFFD for a lone escaped high surrogate. The algorithms are adapted from Newtonsoft.Json (MIT; rust/THIRD_PARTY_NOTICES.md).

## D32 — WPF color text

`colors` implements `ColorConverter.ConvertFromString` (hex `#RGB/#ARGB/#RRGGBB/#AARRGGBB`, the 141 WPF known colors generated from the runtime, `sc#` scRGB) and `Color.ToString()`. AppSettings color getters use `parse_setting` (empty or invalid text is Transparent). scRGB parsing and printing depend on the current culture: list separator, `NumberStyles.Float | AllowThousands` and float formatting. The culture is a native boundary supplied as `NumberCulture`; invariant and de-DE are verified. `ContextColor` strings are always rejected. WPF would try to load the referenced ICC profile from a URI, and the port never opens profile files or URIs from settings. The original writes stored colors with `Color.ToString()`, so this only affects hand-edited or imported values. Parsing rules are adapted from dotnet/wpf (MIT; rust/THIRD_PARTY_NOTICES.md).

## D33 — typed Newtonsoft reads and DateTime.TryParse

`DeserializeObject<T>` is modelled by a typed mode of the `newtonsoft` reader: strings and number text stay raw, and each property applies its own `ReadAs*` rule. `ReadAsString` keeps number text verbatim after validating it. `ReadAsInt32` uses its own number rules and never date-parses strings. `ReadAsDateTime` tries Newtonsoft's ISO and `\/Date()\/` formats before `DateTime.TryParse(text, InvariantCulture, RoundtripKind)`. Unknown members are skipped with `ReadType.Read`, so date or number errors inside them still fail the read. Null elements stay null, and any error fails the whole list.

.NET's `DateTime.TryParse` is an open-ended lexer-driven parser. `dotnet_datetime` implements an explicit grammar covering every form captured from the runtime: Y-M-D, M/D/Y, month/weekday names, two-digit year pivot 2049, 12/24-hour times, fraction rounding, Z/GMT/numeric offsets, `AdjustTimeZoneToLocal` boundary wrapping, and today's local date for time-only or yearless input. Anything outside that grammar is rejected, which would empty a hand-edited folder list that .NET accepts. The app writes only ISO via `SerializeObject`, so only hand-edited values are at risk, and they must match a captured form to load. "Today" is a native boundary, like the time zone. `folder_rules` uses this to port the folder-rule load, normalization, `GetFolderVolumeRules` ordering and add/update/remove/set/match lifecycle, with GUID allocation and the UTC clock injected.

## D35 - immutable portable migration input

`legacy_store::StoreProbe` models `StorageFactory.cs` selection from injected File.Exists results and package identity. Either marker selects portable storage, even in a packaged process; a missing or invalid settings file does not select another backend. Native probes must use the executable directory and reject directories masquerading as marker files.

`PortableSnapshot` owns original bytes separately from the decoded `PortableStore`. This is a read-only migration boundary, with no persistence API. Retaining only a normalized dictionary would lose unknown content, comments, duplicate entries, BOM/encoding and corrupt-but-recoverable input. Source: `DataModel/Storage/StorageFactory.cs`, `Internal/JsonFileSettingsBag.cs`. Registry/package native enumeration and destination persistence remain future work; this does not claim completed migration or app integration.

## D36 - typed profile entry points

The installed profile-list and single-profile import paths use `typed_profiles` rather than serde DTO decoding. `profiles::parse`, `parse_legacy` and `ProfileCollection::import_json` now require the injected `LocalZone` boundary so unknown-member reads and enum date detection follow the same Newtonsoft behavior as other legacy readers. Serde DTO decoding remains useful for canonical internal fixtures, but is not the migration/import parser. Original `VolumeProfileService.ParseProfiles`, `NormalizeProfile` and `ImportProfile` are executed in the reference capture; no native services are started.

## D37 - dynamic custom-theme import and saved-list loading

`Theme::from_json` uses the dynamic Newtonsoft reader with an injected LocalZone; it no longer uses serde's canonical ThemeFile reader. Theme category is nullable because an explicitly null Category survives C# dynamic conversion and export. ThemeFile remains the export shape. Number parsing shares the existing NumberStyles grammar at double precision for Convert.ChangeType opacity conversion. `Theme::load_custom` parses the entire saved list before importing individual items, preserving the original outer/inner catch boundaries.

Reference capture links ColorTheme.cs unchanged and extracts LoadCustomThemes from EarTrumpetColorsSettingsPageViewModel.cs into a model-only harness with an in-memory settings string/list. It starts no WPF windows or real settings services. A constructor-date probe found that untyped JSON must retain the actual Date value; this is now represented in the shared Newtonsoft reader. Typed Read/Skip constructor handling stays unchanged.

## D38 - app-rule lifecycle and ordered effects

`app_rules::AppRules` owns a lazy normalized cache plus the raw current and legacy JSON inputs. Mutations enqueue ordered Write/Changed effects for the future native destination-store/observer adapter. Read-triggered legacy migration can enqueue a Write with no AppRulesChanged notification. Raw JSON assignment invalidates the cache and always queues a write and notification; it preserves nonblank input until a later load or mutation. Legacy import merges through the hard-mute setter and never modifies the old legacy key.

`GetAppRules` sorting uses the current culture in C#, so the core accepts a comparer instead of substituting Rust/ordinal sorting. Capture records actual Comparer<string>.Default comparisons as a boundary oracle independently of the returned sorted lists. Native collation remains subject to MANUAL_TESTS 18. Clock and time zone are injected, no Windows dependency or I/O is added to core. Source: AppSettings.cs AddAppRule/UpdateRule/SetApp*/GetAppRules/CloneRule/RemoveAppRule/ClearAppRules/AppRulesJson/LegacyHardMutedAppsJson and existing loader/migration members.

## D39 - hidden collection lifecycles

`hidden::HiddenApps` and `HiddenDevices` share a private lazy cache/persistence helper and the app-rule clock/time-zone/effect boundary. Public reads return owned copies. Mutations enqueue Write followed by Changed only when the original methods save/notify. No native I/O is added; an eventual app adapter must dispatch each collection's effects to its own destination key/event. Current-culture comparisons remain injected, as for app-rule sorting (D38).

Reference capture extracts AppSettings hidden app/device count, lookup, list, hide/unhide, load and save members verbatim with only UtcNow replaced. ResetHiddenCachesForCapture clears the loaded flags to model fresh-process reload, without altering the source loaders. Rust tests reconstruct fresh collections from the saved JSON for that boundary. The original normalization/deduping occurs only on load, not after every mutation.

## D40 - immutable migration archive and storage adapter crate

Portable migration archives original config/settings.json bytes at executable-relative `config/rust/migration.v1.json`. Future editable overrides use `config/rust/settings.v1.json`. Installed registry/package migration will use `%LOCALAPPDATA%\BetterTrumpet-Rust\migration.v1.json` plus `settings.v1.json` in the same directory. Portable archive persistence was implemented in D40; D41 adds raw registry archival. Packaged adapters and editable overrides remain open; D42 supplies registry decoding as a library, with app startup integration still open.

The archive uses format BetterTrumpet.Rust.PortableMigration, version 1 and a required original_bytes field (null for an absent file, otherwise a JSON byte array). It retains encoding/BOM, duplicate and unknown keys, corrupt input and consent-key presence. Reading delegates to the existing legacy portable bag. No setters/IDs/migrations/default flags run against the original. Missing/empty/loaded/invalid source status is explicit. Invalid or unsupported archives fail without automatic replacement/reimport.

Architecture deviation: added a small `bt-storage` workspace crate for filesystem adapters and tempfile's cross-platform persistence primitive. This keeps `bt-core`'s normal dependency tree free of Windows/UI/OS-adapter dependencies and lets actual file behavior be tested on Linux without building Tauri. The archive codec and decoded snapshot stay in core. bt-storage forbids unsafe Rust; it introduces no COM or network access. Future Windows enumeration must still respect the original COM/Win32 boundaries.

Initialization writes a uniquely named staging file in the destination directory, flushes and syncs it, then uses persist_noclobber. On Windows, the inspected tempfile 3.27 implementation calls MoveFileExW without MOVEFILE_REPLACE_EXISTING. A concurrent winner is loaded rather than replaced. Existing files, including corrupt archives and leftover staging files, remain untouched. No blanket guarantee for every filesystem or power-loss scenario is inferred; NTFS/exFAT deployment and interruption behavior remain MANUAL_TESTS 20. Concurrent writes by the legacy app to its source file also remain a startup-coordination acceptance concern.

## D41 - lossless raw registry capture and archive

Core RegistrySnapshot retains key existence and every value as name_utf16 units, raw u32 type and exact data bytes. The versioned BetterTrumpet.Rust.RegistryMigration archive uses the same no-clobber installation helper as portable migration. bt-storage accepts a read-only capture callback and never invokes it when an archive already exists. No whitelist, XML decoding, environment expansion, key creation or settings setter runs during capture.

The bt-app Win32 shim opens HKCU with KEY_QUERY_VALUE only, enumerates value names and reads payloads with NtQueryValueKey/KeyValuePartialInformation. An actual Windows fixture exposed byte normalization in RegEnumValueW/RegQueryValueExW for an odd-length REG_SZ: [97,0,98] was returned as [97,0,0]. NT queries preserved the stored bytes, so the first attempt was corrected rather than changing fixture expectations. Every unsafe call is confined to the Win32 shim and documented. Native test writes/deletes are cfg(test)-only under uniquely owned Software/BetterTrumpetRustTests subkeys; production capture has no write API.

Capture compares metadata around each enumeration and two complete sorted passes, with bounded retry/error on observed changes. This detects observed concurrent edits, not an atomic registry transaction. Real concurrent-writer/platform acceptance remains script 21. Source-registry value decoding must separately reproduce the original .NET/Win32 getter, including normalization/expansion; raw archival is not that getter.

Primary references: [Microsoft registry sharing table](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys) documents HKCU/Software as shared across views (no Wow6432Node path is invented); [Nt/ZwQueryValueKey](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-zwqueryvaluekey) specifies query access, buffer/status handling and Nt naming for user mode; [KEY_VALUE_PARTIAL_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_key_value_partial_information) defines the three-ULONG header and raw data length. Original app source: RegistrySettingsBag.cs and StorageFactory.cs.

## D42 - effective registry values and runtime-default read requests

`registry_values` projects raw NT bytes to .NET 8 RegistryKey.GetValue objects and exposes original RegistrySettingsBag read/HasKey behavior. It preserves string/multi-string contents as UTF-16 units, including lone surrogates; direct strings are not silently repaired into UTF-8. Request::NullDefaultString selects the original XML route when the runtime string default is null, unlike a nonnull string default. XML reads replace invalid surrogate units with an illegal XML sentinel so the existing streaming decoder fails only if it actually reaches them; unread malformed tails retain the original early-stop behavior.

Native registry upcasing and environment expansion are injected. The bt-app shim implements these with RtlUpcaseUnicodeChar and ExpandEnvironmentStringsW, without reopening the legacy key. GetValue/HasKey supported-type decisions, raw integer lengths, multi-string empty components, NUL handling and expansion error boundaries are captured independently. Ordinary Unicode lowercase/OrdinalIgnoreCase and REG_DWORD/REG_QWORD tag-only decoding are not substitutes.

Native reference capture uses uniquely owned disposable HKCU keys, NT raw writes and real RegistryKey.GetValue. A renamed copy of RegistrySettingsBag keeps Get/HasKey/ReadSetting unchanged; only the key-opening expression selects the read-only fixture key. Process-local test environment variables are restored and keys are deleted in finally. Real user settings and the original source tree remain untouched. Captures are in registry_projection_reference.json, one compact native case per line, with OS/runtime metadata. Native output strings are recorded as UTF-16 arrays so the capture itself does not repair or reject lone surrogates.

The inspected [RegistryKey.cs .NET 8.0.31 source](https://github.com/dotnet/runtime/blob/v8.0.31/src/libraries/Microsoft.Win32.Registry/src/Microsoft/Win32/RegistryKey.cs) and native probes establish the 512-byte initial buffer/pool boundaries. Odd-byte Windows normalization preserves the dangling byte in single-byte and one-byte-short-of-buffer cases; probes cover 511/513, 1023/1025 and 2047/2049. This is pinned to the captured OS/runtime and remains explicit cross-version acceptance in MANUAL_TESTS 21. Library decoding does not itself wire startup, editable settings, packaged storage or live native observers.

## D43 - editable overrides over immutable migration archives

Changes made in the Rust app are stored as overrides in a separate Rust-owned `settings.v1.json` beside the immutable migration archive. The archive and the original store are never rewritten. An override keeps the original bag's representation (a UTF-16 legacy string, or a native boolean for packaged settings), so reads take the same XML/string routes as the source backend. Profile and rule JSON stay byte-exact text. Lookups use the session's key comparer (registry upcasing, or the portable dictionary's comparer). The document is versioned (`format`/`version`), rejects duplicate fields and keys, and keeps unknown top-level and per-entry fields as raw JSON. Updating one setting therefore never drops or re-rounds fields written by a newer build.

`bt-storage::editable` opens without creating anything. A save serializes cooperating writers with a sidecar lock, compares the file with the bytes last loaded or saved, and refuses with `Conflict` if another writer or an external edit changed it. Otherwise it stages, flushes, syncs and atomically replaces only that file. A failed save leaves the in-memory document and the existing file untouched; reload-and-merge policy belongs to the app layer. Packaged-setting overrides read through the registry route are rejected explicitly rather than guessed.

## D45 - packaged (MSIX) settings capture

The original MSIX build stores settings in its package's LocalSettings (`xammen.Bettertrumpet`, publisher `CN=7EDFC72A-8780-4841-8F34-30B45D719EAF`). The Rust build computes that family with `PackageFamilyNameFromId` and reads the container from outside the package with `ApplicationDataManager.CreateForPackageFamily`. This was verified to work unprivileged and read-only: a family that isn't installed fails with "file not found" and creates nothing. Capture records every entry, with booleans and strings exact (UTF-16) and any other WinRT type kept by type code only, and takes two identical passes to avoid a container being written mid-read. It is archived like the registry snapshot (`PackageMigration` format), and reads follow WindowsStorageSettingsBag: native bool/string casts, XML for other kinds, XML errors surface as `Throws`, and other types read as the default. Key lookup is case-insensitive like the container. Ordinal ignore-case is the working comparer; non-ASCII casing equivalence is unverified because the probe could only read existing keys. The WinRT reads live in the bt-app Win32 shim, which keeps a process MTA via `CoIncrementMTAUsage`. No packaged BetterTrumpet is installed on the development machine, so end-to-end migration from a real MSIX install is MANUAL_TESTS 23.

Priority is now the features people use most, delivered in the running app, ahead of milestone-ordered compatibility work. Settings migration and parity research pause where they are (their libraries stay tested and committed) and resume once the everyday feature set is in place. First batch: default-device switching (flyout button plus tray-menu device list, console and multimedia roles via IPolicyConfig as the original), FileDescription app names, executable icons, a live tray tooltip, single instance, and a "Start with Windows" toggle stored under its own Run value name (`BetterTrumpet Rust Preview`) so the C# app's `BetterTrumpet` entry is never touched. Audio commands are async so polling never blocks the UI thread; the tray menu and tooltip refresh from a devices-only poll every second.

## D47 - build features now, test in a later pass (user decision, 2026-10-26)

Features are built back to back. Each one gets only a compile check (`cargo build`, plus clippy when it is cheap) and a commit; no new automated tests, fixture captures or screenshot verification per feature. Anything that needs checking is listed in MANUAL_TESTS.md, and all testing happens in one dedicated pass the user will schedule. Existing tests stay in place. This supersedes the per-milestone "tests pass" gates for the feature-first phase (D46).

## D48 - native Win32/Direct2D UI instead of Tauri (user decision, 2026-10-28)

Footprint matters most, so the tray-resident UI is native. This supersedes D05, D07 and D08 for the tray, flyout, media popup and tooltip, and the webview half of D09. The app no longer uses Tauri or WebView2: a Win32 message loop on one UI thread, Shell_NotifyIcon (NOTIFYICON_VERSION_4, re-added on TaskbarCreated), RegisterHotKey, TrackPopupMenuEx menus, a named mutex for single instance, and layered windows (`AllowsTransparency` in the original) drawn with software Direct2D and DirectWrite into a DIB and shown with UpdateLayeredWindow. Acrylic is the original's SetWindowCompositionAttribute accent policy (DrawAllBorders), with DWM corner rounding. Software rendering keeps the process free of a Direct3D device; windows only redraw while something changes and release their pixels when hidden. Measured at first launch (release build, idle in the tray): one process, 4.2 MB private, 26 MB working set, 0 ms CPU over 10 s, against about 199 MB private across ten processes for the WebView2 build. The settings window is not ported yet; whether it is native too or reuses the original's React UI in a webview created on demand is decided when it is built. Unsafe code stays in the bt-app Win32 shim (`win32/`), with the drawing, window, tray, menu, sound and instance adapters there. `--render <dir>` draws each window to PNGs without showing anything, for checking the drawing without taking over the screen.

## D49 - the port's own log and diagnostics folders

Logs and diagnostic reports of the Rust build live under `%LOCALAPPDATA%\BetterTrumpet-Rust\{logs,diagnostics}`, so the original's `%APPDATA%\BetterTrumpet` is never written. Reports are local files only; nothing is uploaded.

## D50 - the tray animation rests when nobody can see it

The playback animation shows the original's poses at its 50 ms frame times, but its timer fires only when the pose changes (device glyphs hold each pose for two frames; the speaker holds full waves for six), each pose's icon is made once per loop, and only the image is sent to the shell. It pauses while the display is off (GUID_CONSOLE_DISPLAY_STATE), while the session is locked or a screen saver runs, and while a full-screen app is in front on the taskbar's monitor (SHQueryUserNotificationState, asked at most once a second while playing). Nothing visible changes.

## D51 - AnimateTrayIcon, a port-only switch for the tray animation

Settings > Performance > Animations has "Animate the tray icon while media plays" (on by default, so the original's behaviour is unchanged). Off, the icon stays still and the animation's timer never runs. The key lives only in the port's `settings.v1.json`; the C# app has no such setting, so it is not part of .btsettings export/import and is left out of the C# compatibility snapshot.

## D52 - windows give their memory back when they close

The settings, mixer and onboarding windows each get their own Direct2D factory, so the software rasterizer's buffers and caches are freed with the window instead of staying with the tray's shared one. A second after the last of them closes, the shared text-layout cache is cleared, every heap releases its free pages (HeapOptimizeResources, HeapCompact) and the working set is trimmed. The executable opts into the segment heap. Measured with Settings opened and closed three times: about 16 MB private while open, back to about 6 MB (baseline 4.6 MB) a few seconds after closing, with a private working set under 1 MB. Before: about 14 MB stayed.

## D53 - Eco Mode stops the tray animation; AutoEcoMode reads the power source

Effective Eco Mode (EcoMode, or AutoEcoMode on battery) keeps the tray icon still, and the AnimateTrayIcon switch (D51) shows "Overridden by eco mode". The battery state comes from GetSystemPowerStatus, refreshed on PBT_APMPOWERSTATUSCHANGE; switching power source reloads the peak-meter rate, the tray animation and the settings page. (Before this, the port always reported mains power, so AutoEcoMode never took effect.)

## D54 - this project's links, ShowProjectLinks, onboarding on first launch

"Report a problem" (tray menu and Settings > About) opens this repository's new-issue page; Settings > About also links this repository and the original BetterTrumpet. The tray menu's "Star on GitHub" is a submenu with this project and the original; ShowProjectLinks (port-only, on by default; Settings > General > Tray Icon) hides it, while "Report a problem" stays. The addresses live in `bt_app::links`.

The setup window opens on the first launch when HasShownFirstRun is unset, meaning the PC never ran EarTrumpet, BetterTrumpet or this app (the original's Q09 launch stays silent); Left Ctrl at startup and the tray item still open it later.

## D55 - opt-in update check against this project's releases (user decision, 2026-10-29)

The app's only network request. Like the original's UpdateService it checks 10 s after startup and then every 6 hours, filtered by UpdateNotifyChannel, but it asks `api.github.com/repos/tokenbroker/BetterRustTrumpet/releases` (the list, because `releases/latest` leaves out pre-releases) through WinHTTP, and it only tells: a tray menu item and Settings > Updates open the release page; nothing is downloaded or installed. Drafts never count, pre-releases only for a pre-release build, versions compare as SemVer, and only this repository's release pages are opened. The request carries the app's name and version as its user agent and nothing else. On battery with Eco Mode the timed check waits an hour; Settings > Updates' Check button always checks.

The switch is a port-only key, CheckGitHubForUpdates, off by default, so settings carried over from the original (whose AutoCheckForUpdates defaults to on) never start the request. Onboarding's Privacy page offers it, ticked on a first launch. The workspace version now follows the release tags (0.1.0-alpha.3), and the release workflow refuses a tag that differs from it.
